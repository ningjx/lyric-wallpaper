# 壁纸性能优化方案

> 版本：v1 · 2026-09-07
> 状态：Stage 0 已完成；Stage 2 因当前 renderer 的不透明场景依赖而暂缓；Stage 5 已取消
> 范围：`wallpaper/src/liquid/` 与其渲染器适配层
> 约束：不降低默认视觉效果、不改变歌词同步与配置属性语义、不迁移 WebGL 版本。

---

## 1. 目标与原则

### 目标

在不改变当前默认视觉效果的前提下，降低 Wallpaper Engine 运行时的 GPU 占用、CPU 占用、功耗和背景切换卡顿，并保持所有现有功能可用：

- 歌词逐行滚动、提前收敛和同步偏移；
- 深度缩放、透明度、玻璃折射、高光、阴影及“歌词在玻璃后”模式；
- 背景布局、随机背景轮播、缩放和偏移；
- 所有既有 Wallpaper Engine 属性与参数面板配置。

### 实施原则

1. **先测量、后优化**：每阶段先增加可观测数据，再根据实测决定是否继续。
2. **默认画面一致**：默认参数、默认渲染路径和截图像素差异必须在设定阈值内。
3. **小步可回退**：每项优化独立提交，保留开关或旧路径至少一个发布周期。
4. **优先减少工作量**：先消除无效帧和全屏重绘，再考虑 API 或渲染技术升级。

---

## 2. 当前渲染链路与已知瓶颈

当前液态壁纸的运行路径如下：

```text
requestAnimationFrame（持续运行）
  → ReferenceLyricsWallpaper.draw()
  → renderer.setScrollY(scrollY)
  → renderer.render()
  → 全屏背景绘制至场景 FBO
  → 逐项绘制玻璃卡片 / 歌词 / 高光 / 阴影
  → 全屏复制到默认帧缓冲
```

### P0：静止时仍持续请求重绘

`draw()` 每个动画帧都会调用 `setScrollY()`；上游渲染器的该方法会请求一次 render，即使滚动值未变。歌词在两句之间已经停稳时，仍会持续执行完整场景绘制。

**影响**：这是默认播放路径中最明确的持续功耗来源，优先级最高。

### P1：静态背景参与每次动态合成

背景图在下一次切换前不会变化，但当前每次 render 都绘制背景到全屏 FBO 并最终全屏复制。歌词滚动时，动态区域通常只有数张歌词卡片，背景的重复处理没有视觉收益。

### P2：滚动期间高频重建配置

滚动超过很小阈值便重建可见歌词的文字/玻璃配置。上游有前景纹理和逐元素 FBO 缓存，但字号、透明度、玻璃强度连续变化时，缓存仍可能失效。

### P3：背景合成包含 PNG 中转

背景布局目前经过 Canvas 绘制、PNG Blob 编码、图像解码和纹理上传。它不构成持续帧开销，但大图切换时会增加主线程卡顿和内存峰值。

## 3. 基线测量与验收规范（Stage 0）

任何视觉路径修改前，先建立基线。渲染器已有性能监控能力，需通过本地适配层暴露只读统计，不进入正式用户界面。

当前实现：控制台可通过 `window.lyricWallpaperPerformance.setEnabled(true)` 开启统计，
`snapshot()` 获取 rAF/实际 render 频率、帧耗时、draw call、缓存命中与当前管线；调用
`reset()` 开始新的采样窗口。调试 URL 追加 `?perf=1` 可在启动时直接启用。

### 采样场景

| 场景 | 时长 | 用途 |
|---|---:|---|
| 无歌词 / 无播放 | 60 秒 | 检查空闲帧与资源释放 |
| 两句歌词之间、滚动已停稳 | 60 秒 | 验证空闲渲染归零 |
| 普通歌词切换 | 连续 10 次 | 检查滚动流畅与峰值帧耗时 |
| 长歌词 + 高光/阴影开启 | 连续 10 次 | 压力场景 |
| 背景轮播 / 4K 背景切换 | 5 次 | 检查卡顿、内存和竞态 |
| `lyricBehindGlass` + 高质量模糊 | 连续 5 次 | 兼容路径 |

### 指标

- render 次数/秒、rAF 次数/秒；
- 平均与 P95 帧耗时、掉帧次数；
- 每帧 draw call、玻璃元素缓存命中率、模糊 pass 数；
- Canvas CSS 尺寸、实际像素尺寸、DPR；
- 浏览器/Wallpaper Engine 的 CPU、GPU、显存占用（以同一机器、同一分辨率横向比较）；
- 歌词时间误差与视觉截图比对。

### 全局验收门槛

- 默认预设在视觉回归截图中不出现可见差异；
- 歌词行切换时间误差不超过现状；
- 不播放和停稳状态不应产生连续 GPU render；
- 出现 WebGL 上下文丢失、背景加载失败或兼容错误时，保留现有 CSS fallback。

## 4. 分阶段优化计划

### Stage 1 · 消除无效重绘（P0，最高优先级）

**目标**：画面静止后让 GPU render 归零；不改变滚动曲线和歌词切换时机。

**改动策略**：

1. 在适配层记录上次提交给 renderer 的 `scrollY`；仅当值变化超过视觉阈值时调用 `setScrollY()`。
2. 弹簧已经满足现有停靠条件时，不再提交滚动更新。
3. 保留 rAF 对本地时钟和下一句歌词的计算；但当 renderer 无 dirty 状态时，`render()` 必须快速返回。
4. 将阈值定义为常量并保守设置，首版建议不高于 `0.05 CSS px`，以避免改变现有视觉曲线。

**不改动的部分**：歌词索引算法、`springStepCritical` 参数、`getScrollLeadSeconds()`、滚动收敛阈值。

**验收**：

- 两句歌词之间的 rendered FPS 下降至 0；
- 滚动阶段的歌词位置与修改前录像/截图一致；
- 不发生首帧遗漏、歌曲暂停后不刷新、恢复播放不同步。

**回退**：以一个内部 feature flag 保留“每帧提交 scroll”的旧路径。

---

### Stage 2 · 静态背景层与动态歌词层分离（P1，高优先级）

**当前结论**：已做透明叠层验证，但玻璃 shader 仍依赖不透明场景 FBO 的合成结果；透明输出会导致玻璃主体与折射失效。因此已回退该实验，待本地 renderer adapter 能完整提供场景背板后再继续，不以牺牲现有效果换取性能。

**目标**：背景未变化时不参与动态歌词帧的全屏渲染。

**推荐架构**：

```text
背景层（静态）
  - 屏幕显示的背景图
  - 供玻璃折射采样的只读 WebGL 纹理
  - 仅在背景、布局、缩放、偏移、窗口尺寸或 DPR 变化时更新

歌词层（透明 WebGL Canvas，动态）
  - 玻璃卡片、歌词文字、高光、阴影
  - 仅在歌词滚动、歌词内容或材质参数变化时绘制
```

**实现策略**：

1. 新增本地 `renderer-adapter`，由它统一管理背景变换矩阵；屏幕背景与 shader 背景采样共享同一套变换参数。
2. 将顶层 WebGL Canvas 改为透明输出；背景使用单独 DOM/CSS 层或静态底图 Canvas 显示。
3. 玻璃 shader 继续采样同一张已上传的背景纹理，因此折射效果保持不变。
4. 默认的 `isolateBackdrop` 语义保持：玻璃折射背景，而不强制让多张玻璃互相折射。
5. 保留旧的“全场景 FBO 合成”路径作为兼容回退；根据配置和功能自动选择。

**兼容处理**：

- `lyricBehindGlass`：为单行歌词使用局部 FBO，先绘制文字再绘制玻璃，不能直接套用透明顶层路径。
- `separableBlur`：继续使用现有全屏背景 FBO 路径。该模式属于高质量路径，不在第一版分层中强行改写。
- 背景布局：cover / contain / stretch / tile 的坐标必须由同一函数计算，避免玻璃内外背景错位。

**验收**：

- 默认模式下动态帧不再包含全屏背景绘制；
- 背景与玻璃折射位置一致；
- 四种背景布局、随机轮播、缩放/偏移以及窗口 resize 全部通过；
- `lyricBehindGlass` 和高质量模糊自动走正确的兼容路径，效果不变。

**风险与回退**：透明混合、不同 CEF 版本的 alpha 行为、背景位置错位。通过 `renderPipeline: auto | layered | scene-fbo` 内部开关回退到现有路径。

---

### Stage 3 · 减少滚动期配置与纹理更新（P2，中优先级）

**目标**：降低歌词滚动时的 CPU 对象分配、Canvas 文字栅格化和玻璃缓存失效频率，同时保持动画连续。

**改动策略**：

1. 把稳定内容（歌词文字、原始矩形、固定材质）与动态状态（scrollY、alpha、scale）分离。
2. 默认仅维护当前行与相邻行；保留现有 `lyricDepthCullDistance` 的用户语义与范围。
3. 对视觉变化做分档或 rAF 合帧：只有透明度/缩放跨越不可见阈值时才更新缓存签名；位置继续平滑移动。
4. 缓存文字度量与字体纹理。现有文字度量缓存继续保留，避免扩大到逐帧 `getImageData()`。
5. 参数滑块的 `input` 事件合并至下一帧；涉及背景、DPR、尺寸重建的项目延迟到用户停止拖动后执行一次完整更新。

**验收**：

- 当前行切换期间无可感知的阶梯式缩放或透明度跳变；
- 长歌词与中英文混排不出现裁切或文字错位；
- 同一滚动片段中的前景栅格化次数、玻璃 cache miss 数低于基线。

---

### Stage 4 · 背景纹理直传（P3，中优先级）

**目标**：降低背景切换时的卡顿和中间内存占用。

**改动策略**：

1. 移除 Canvas → PNG Blob → 再解码的中转链路。
2. 背景已绘制到 Canvas 时，直接以 Canvas / `ImageBitmap` 作为 `texImage2D` 的来源上传到 WebGL。
3. 后续可将布局计算移入 shader，使原始背景纹理只上传一次；但该项必须在分层背景路径稳定后再评估。
4. 保持现有 `file:///` 背景加载 fallback 与请求序号防竞态逻辑。

**验收**：

- 背景切换不会显示黑帧或旧图回闪；
- 快速连续调节背景参数时不会泄漏 Object URL 或纹理；
- 大图切换的主线程长任务、峰值内存低于基线。

## 5. 暂不实施的方案

### WebGL 2 迁移

当前 renderer 创建的是 WebGL 1 上下文。WebGL 2 可带来更现代的 FBO、纹理和 GLSL 能力，但它需要着色器与资源路径整体迁移，并须在 Wallpaper Engine 的实际 CEF 环境逐机验证。

当前主要损耗来自无效帧、全屏背景重复合成和效果 pass，而不是 WebGL 1 API 本身。因此在 Stage 1–4 完成并取得基线数据前，不启动迁移。后续如需评估，应做“WebGL 2 优先、WebGL 1 回退”的独立原型，不能直接替换现网路径。

### 完整复制上游 renderer

当前直接从子模块导入不产生额外运行时网络成本，构建产物已将所需模块打包。完整复制会提高合并上游修复的成本，暂不推荐。

推荐保留子模块，并建立小型本地适配层承载本项目专属的帧调度、背景分层、质量预设和统计接口；只有确实需要改动核心渲染管线时才 fork。

## 6. 建议的提交与验证顺序

1. `perf: add renderer measurement hooks`：只增加调试统计与基线记录。
2. `perf: avoid redundant scroll render requests`：完成 Stage 1，逐项回归。
3. `refactor: introduce wallpaper renderer adapter`：不改变输出，仅建立边界。
4. `perf: split static background from lyric overlay`：完成 Stage 2，保留 FBO 回退。
5. `perf: coalesce lyric visual updates`：完成 Stage 3。
6. `perf: upload composed backgrounds without PNG round-trip`：完成 Stage 4。

每个提交都应执行：

```powershell
cd wallpaper
npm test -- --run
npm run build
```

并完成本文件第 3 节对应的实机场景验证。
